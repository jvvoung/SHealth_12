## 재사용 — 결함 분석만 다시 실행할 때

아래 블록을 Cursor에 붙여넣고, 소스·테스트·요구사항 문서를 컨텍스트로 첨부한 뒤 실행하세요.  
`[T]`에 **실제 ctest 실패 로그**를 붙여넣으면 TC별 기대/실제 분해가 정확해집니다.

```
@src/test/cpp/SHealthBMITest.cpp
@src/main/cpp/BmiTypes.h
@src/main/cpp/BmiCalculator.cpp
@src/main/cpp/CsvReader.cpp
@src/main/cpp/DataImputer.cpp
@src/main/cpp/BmiStatistics.cpp
@src/main/cpp/SHealth.cpp
@docs/requirements_analysis.md
@docs/test_plan.md

[P] 디버깅과 결함 분석에 능한 C++ QA 엔지니어입니다.
    BMI 경계값·연령대·결측 보정·통계 집계 불일치를 파이프라인 단위로 추적합니다.

[C] SHealth BMI C++17, Google Test, CMake, ctest
    - 테스트: src/test/cpp/SHealthBMITest.cpp
    - 실행: cd build && ctest --output-on-failure
    - 파이프라인: CsvReader::load → DataImputer::imputeMissingValues
                  → BmiCalculator::applyToAll → BmiStatistics::compute
                  (SHealth::processFile 고정 순서)
    - 도메인 불변식:
      · BMI 분류: ≤18.5 저체중, 18.5<~23 정상, 23≤~25 과체중, ≥25 비만 (25.0 포함)
      · height≤0 → bmi=0, bmi≤0 → 통계·ID 목록 제외
      · weight=0·height=0 → 동 연령대 평균 보정 (validCount=0이면 미보정)
      · processFile 실패 → -1, invalid typeCode → getBmiRatio 0.0

[T] (여기에 ctest 실패 로그를 붙여넣을 것)

    1) 실패 TC별 요약
       - 테스트명, assertion 종류(EXPECT_EQ / EXPECT_NEAR / ASSERT_*)
       - 기대값 vs 실제값 (숫자는 소수 3~4자리, enum은 BmiCategory명)
       - 실패가 단일 TC인지 연쇄 실패(cascade)인지

    2) 결함 위치 특정
       - 파이프라인 단계(CsvReader / DataImputer / BmiCalculator / BmiStatistics / SHealth)
       - 파일명:줄번호 + 함수명
       - README·requirements_analysis.md 대비 명세 위반 여부

    3) 결함 심각도 분류 (Critical / Major / Minor / Info) 및 근거
       - Critical: 크래시, 0 나누기, BMI 25.0 미분류, 데이터 손실
       - Major: 통계·비율 오류, 보정 실패, API 계약 위반
       - Minor: 부동소수 허용오차, 테스트 데이터·네이밍 이슈
       - Info: 테스트 기대값 오류·문서 불일치 가능성

    4) 최소 변경 수정 방안 (C++17 스타일)
       - 프로덕션 코드 우선 수정; 테스트 오류면 TC 수정 근거 명시
       - 단, 아래 변경 금지:
         · HealthRecord 필드(id, age, weightKg, heightCm, bmi) 의미·이름 변경
         · SHealth public API 시그니처 변경 (processFile, getCategoryRatio 등)
         · BmiThresholds / AgeDecade / LegacyTypeCode 상수값 임의 변경
       - SRP 유지: 수정은 해당 모듈에 국한, God Class 재발 금지

    5) 회귀 검증
       - 영향받는 TC 목록 (실패 TC + 인접 경계 TC)
       - 수정 후 전체 ctest Green 여부

[F] Markdown 분석 보고 (표 + bullet) + 수정 diff 제안
    + cmake --build build && cd build && ctest --output-on-failure Green 확인 절차
    (가능하면 직접 빌드·테스트 실행 후 결과 반영)
```

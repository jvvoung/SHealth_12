## Executive Summary

SHealth BMI 레거시 C++ 프로젝트는 **9단계 QA 워크플로**(`.cursorrules` → 요구분석 → 3차 리팩토링 → 테스트 계획 → TC 구현 → 결함 분석 → 기능 개선 검증 → Golden Master → 종합 검토)를 통해 **God Class·Critical 버그 7건·FAIL() 스텁** 상태에서 **SRP 6모듈·37건 Green·활성 프로덕션 결함 0건·실데이터 E2E 회귀**까지 도달했습니다.

|------|-----------------|--------------|
| 아키텍처 | `SHealth` God Class | **6클래스 SRP** (파사드 + 5모듈) |
| Critical 버그 | 25.0 미분류, 0 나누기 등 **7건** | **0건** (수정·TC 고정) |

**종합 판정:** P0/P1 테스트 목표 **100% 달성**, FI-01~04 **검증 완료**, Golden Master **운영 가능**. 잔여 과제는 **P2 TC(3건)·G3 커버리지 CI 게이트·레거시 temp CSV 통일**입니다.

**핵심 교훈:** 요구분석 선행 + 경계값 TC + 리팩토링 Green 게이트 + `.cursorrules` + Golden Master 조합이 레거시 C++ QA에 효과적이었으며, Cursor AI는 TC 초안·결함 root cause·문서화에 기여했으나 **부동소수 기대값·과잉 리팩터링**에는 사람의 검증이 필수입니다.

## §5. 다음 레거시 C++ 프로젝트 Best Practice 5가지

### BP-1. 요구사항 분석을 TC 설계보다 먼저

- README·레거시 코드 3-way 대조 → **경계값 매트릭스**(BMI 18.5/23/25, 연령 19/71/80)를 표로 고정
- 본 프로젝트: `requirements_analysis.md` 없이 TC 확장 시 **TC-22 픽스처 오류(D-01)** 재발 가능

### BP-2. 경계값·실패 경로 TC를 P0로

- off-by-one(22.99, 24.99, 25.0), `processFile(-1)`, `bmi≤0` 통계 제외를 **최우선** 구현
- 레거시 Critical 7건 중 4건이 **경계·0 나누기** — 단위 TC로 재발 방지

### BP-3. 리팩토링 Green 게이트 (G0)

- **매 차수 ctest Green 후** 다음 리팩토링 — 1~3차에서 10 TC가 기준선 역할
- `.cursorrules`에 "테스트 Green 없이 리팩토링 금지" 명문화 (Step 1)

### BP-4. `.cursorrules`로 AI·팀 거버넌스 통합

- 도메인 절대 규칙(BMI 25.0=Obesity), SRP 모듈 경계, 레거시 API 계약을 **단일 파일**로
- 3차 설계 역행(categoryFromTypeCode invalid) **재발 방지**

### BP-5. Golden Master로 실데이터 E2E 회귀

- 단위 37건으로도 **CLI 출력·대용량 통계 drift**는 놓칠 수 있음
- `shealth.dat` + stdout golden + CI 아티팩트로 **의도적 변경 vs 버그** 분리 (`UPDATE_GOLDEN` 로컬만)
